# 1. Анализ предметной области и существующих решений

\ 

## 1.1. Постановка задачи

\ 

Задача системы состоит в следующем: получив фотографию объекта (автомобиля) и текстовое описание желаемого изменения, система должна:

::: {custom-style="MyBulletList"}
найти подходящий товар в каталоге;
:::

::: {custom-style="MyBulletList"}
автоматически выделить область на фото, которую нужно изменить;
:::

::: {custom-style="MyBulletList"}
сгенерировать фотореалистичное изображение с применённым товаром.
:::

При этом пользователь не должен выполнять никаких ручных операций — ни разметки маски, ни выбора параметров модели.

Задача относится к классу задач условной генерации изображений с ограничениями: результат должен быть фотореалистичным, соответствовать референсному изображению детали, не изменять области вне маски и соответствовать исходному освещению и перспективе сцены. Дополнительная сложность — неопределённость запроса: пользователь может написать «поставь карбоновый спойлер» или «смени диски на чёрные», не указывая конкретную позицию из каталога. Система должна самостоятельно интерпретировать намерение, найти подходящий товар и выполнить все шаги пайплайна.

\ 

## 1.2. Обзор существующих систем визуализации товаров

\ 

Задача визуализации товара на объекте покупателя решается в нескольких коммерческих продуктах, каждый из которых использует собственный технологический подход.

**Zalando** в 2024 году запустил пилот 3D-примерочной: пользователь указывает рост, вес и параметры фигуры, после чего система генерирует персонализированный аватар и отображает одежду с учётом посадки и складок ткани. В апреле 2025 года Zalando приобрёл стартап DeepAR — крупнейшего европейского поставщика AR-примерки — для формирования собственного каталога цифровых двойников одежды. Система работает только с брендами, предоставившими 3D-модели своих изделий; произвольный каталог не поддерживается.

**IKEA Place** — AR-приложение на базе Apple ARKit и Google ARCore, позволяющее разместить мебель в реальном интерьере через камеру смартфона. Система строит 3D-карту помещения в реальном времени и накладывает модель мебели с соблюдением масштаба и освещения. Ограничение аналогичное: для каждой единицы товара требуется профессионально подготовленная 3D-модель, что делает решение неприменимым для длинного хвоста каталога.

**Amazon Virtual Try-On** — инструмент примерки одежды, запущенный в 2023 году. Пользователь загружает собственное фото, система с помощью диффузионных моделей накладывает выбранную вещь с адаптацией к позе и фигуре. По данным Amazon, внедрение инструмента снизило возвраты в категории одежды на 15–25% среди пользователей, воспользовавшихся примеркой. Принципиальное ограничение — система заточена исключительно под одежду и не применима к другим категориям.

**Google Virtual Try-On** (обновлён в 2025) — реализован на базе диффузионной модели, разработанной командой Google Research. Принимает фото пользователя и изображение одежды, генерирует результат примерки с сохранением деталей ткани, паттернов и текстуры. Доступен в Google Search и Google Shopping. Область применения ограничена одеждой и обувью.

**Snap AR** — платформа дополненной реальности, используемая сотнями брендов (Nike, MAC, Gucci) для примерки обуви, очков, украшений и макияжа через фронтальную камеру смартфона. Основана на распознавании лица и рук в реальном времени. Требует разработки отдельного Lens под каждый товар и не поддерживает пользовательский контент.

**Vue.ai** — B2B-платформа для ритейлеров, автоматически генерирующая lifestyle-контент: помещает товар на модель или в интерьер без фотосессии. Заточена под fashion и home decor, работает с каталогами, но не поддерживает загрузку собственной фотографии покупателем.

**Общие ограничения** всех перечисленных решений:

::: {custom-style="MyBulletList"}
заточенность под конкретные категории товаров (одежда, мебель, косметика);
:::

::: {custom-style="MyBulletList"}
необходимость специально подготовленных 3D-моделей или размеченных датасетов для каждого товара;
:::

::: {custom-style="MyBulletList"}
отсутствие поддержки произвольного пользовательского запроса на естественном языке;
:::

::: {custom-style="MyBulletList"}
отсутствие сквозной автоматизации: пользователь самостоятельно выбирает товар и область применения.
:::

Ни одна из рассмотренных систем не решает задачу, сформулированную в данной работе: автоматически интерпретировать текстовый запрос, найти товар в каталоге и визуализировать его применение на произвольном пользовательском фото без ручной разметки.

## 1.3. Методы сегментации изображений

\ 

Для выделения области применения товара на фото требуется решить две задачи последовательно: локализовать объект по текстовому описанию и построить точную маску его контура.

### 1.3.1. Принцип работы моделей сегментации

Сегментация изображений — задача присвоения каждому пикселю изображения метки, указывающей, к какому объекту или классу он принадлежит. В контексте данной работы требуется *инстансная* сегментация: выделение конкретного экземпляра объекта (например, «задний бампер этого автомобиля») в виде бинарной маски.

Современные модели сегментации, как правило, строятся на архитектуре *encoder–decoder*: энкодер извлекает иерархические признаки из изображения, декодер восстанавливает пространственное разрешение и предсказывает маску. Ключевой метрикой качества является **IoU** (Intersection over Union) — отношение площади пересечения предсказанной и эталонной масок к площади их объединения. Значение IoU=1,0 соответствует идеальному совпадению, IoU≥0,5 считается приемлемым результатом для большинства прикладных задач.

### 1.3.2. Сравнение моделей семейства SAM

**SAM 1** (Meta AI, 2023) — первая универсальная модель сегментации с открытыми весами. Принимает подсказки в виде точек, bounding box или частичной маски и возвращает бинарную маску объекта. Архитектурно состоит из ViT-энкодера изображения, лёгкого энкодера подсказок и mask decoder на основе двустороннего трансформера. Недостатки: работает только с изображениями, не поддерживает видео; ViT-H вариант требует значительных вычислительных ресурсов.

**SAM 2** (Meta AI, июль 2024) — расширенная версия с поддержкой видеосегментации на основе потоковой памяти (*streaming memory*). Ключевое архитектурное нововведение — memory encoder и memory attention: модель сохраняет признаки предыдущих кадров и использует их для поддержания трекинга объекта во времени. На изображениях SAM 2 работает в 6 раз быстрее SAM 1 при более высоком качестве (61,4% mIoU против 58,1% по бенчмарку SA-23). Поддерживает частично перекрытые объекты и сложные фоны. Выбран в данной работе как актуальный стандарт на момент разработки системы.

**SAM 3** (Meta AI, ноябрь 2025) — выпущен после завершения основной разработки системы. Ключевое нововведение: нативная поддержка текстовых промптов, что устраняет необходимость в отдельном детекторе. Включает decoupled detector–tracker архитектуру и датасет из 4 млн уникальных концептов. Представляет интерес для будущих версий системы как замена связки SAM 2 + GroundingDINO.

### 1.3.3. Сравнение детекторов с открытым словарём

Для передачи SAM 2 координат объекта по текстовому запросу требуется отдельный детектор, способный локализовать произвольный объект без заранее заданного набора классов — так называемый *open-vocabulary detector*.

**GLIP** (2022) — одна из первых моделей, объединивших детекцию и языковое заземление. Использует одностадийный бэкбон, что ограничивает глубину слияния визуальных и текстовых признаков и снижает точность при сложных текстовых запросах.

**OWL-ViT / OWLv2** (Google) — прикрепляет классификационные головы к ViT-бэкбону. Рекомендуется для задач с часто меняющимся набором классов, однако уступает GroundingDINO по точности на zero-shot бенчмарках COCO и LVIS.

**GroundingDINO** (IDEA Research, ECCV 2024) — превосходит как GLIP, так и OWL-ViT на zero-shot бенчмарках за счёт более глубокого слияния модальностей. Архитектура строится на базе DINO-детектора с добавлением *feature enhancer* и *cross-modality decoder*: текстовые и визуальные признаки обмениваются информацией на нескольких уровнях сети, что позволяет модели точно сопоставлять фразы из запроса с регионами изображения. Имеет официальную интеграцию с SAM 2 в виде пайплайна Grounded SAM 2. Выбран в данной работе как наиболее точный открытый детектор с текстовым управлением.

### 1.3.4. Итоговая связка

В системе используется Grounded SAM 2: GroundingDINO локализует объект по текстовому запросу пользователя и возвращает bounding box; SAM 2 строит точную бинарную маску по полученному bounding box. Это позволяет сегментировать произвольные объекты без дообучения на специализированных датасетах — достаточно текстового описания на естественном языке.

## 1.4. Диффузионные модели инпейнтинга

\ 

### 1.4.1. Принцип работы диффузионных моделей

Диффузионные модели относятся к классу генеративных моделей, основанных на двух процессах: *forward diffusion* и *reverse diffusion*. В прямом процессе к исходному изображению последовательно добавляется гауссовский шум до тех пор, пока изображение не превратится в чистый шум. Обратный процесс — функция, которую обучает нейронная сеть: предсказать предыдущий (менее зашумлённый) шаг по текущему состоянию и текстовому условию. После обучения генерация нового изображения сводится к итеративной денойзинг-процедуре: начиная с чистого шума, модель шаг за шагом восстанавливает изображение, соответствующее промпту.

Для инпейнтинга задача формулируется иначе: шум добавляется только в замаскированную область, а остальные пиксели фиксируются. Модель обучается заполнять маскированную зону так, чтобы результат был согласован с контекстом вокруг маски.

Ранние диффузионные модели для инпейнтинга (Stable Diffusion 1.5, SDXL) используют архитектуру U-Net в качестве денойзера. U-Net содержит энкодер-декодер со skip-connections, что обеспечивает сохранение пространственных деталей. Принципиальное ограничение U-Net-архитектуры — ограниченное рецептивное поле: модель хуже улавливает глобальные зависимости между удалёнными частями изображения.

**FLUX** (Black Forest Labs) использует принципиально иную архитектуру — *Multimodal Diffusion Transformer (MMDiT)*. Вместо U-Net применяются трансформерные блоки с механизмом двунаправленного внимания между текстовыми токенами и патчами изображения. Это позволяет каждому патчу изображения «видеть» все остальные патчи и все токены промпта одновременно, что радикально улучшает семантическое понимание и глобальную когерентность генерации. FLUX также использует *flow matching* вместо классического DDPM-шедулера, что ускоряет процесс обратной диффузии.

### 1.4.2. Обзор исследованных моделей

В рамках работы исследованы и реализованы модели трёх классов — маскированный инпейнтинг, мультиизображённое редактирование и img2img.

**Маскированный инпейнтинг**

Классический подход: модель получает исходное изображение, бинарную маску (белая область = регион редактирования) и текстовый промпт.

**SDXL Inpainting** — полностью открытая модель (~7 ГБ), запускается локально без GPU-сервера, не требует токена HuggingFace. Оптимальное разрешение 1024×1024. Преимущество: компания может развернуть модель на собственной инфраструктуре без передачи данных сторонним сервисам. Недостаток: слабое понимание референсного изображения детали, склонность к галлюцинациям при нестандартных объектах.

**FLUX.1 Fill Dev** — модель на базе трансформерной архитектуры (~20 ГБ), значительно превосходит SDXL по качеству маскированной генерации благодаря глобальному вниманию MMDiT. Распространяется с открытыми весами, доступна для самостоятельного хостинга. В практических тестах показала нестабильные результаты при наличии референсного изображения — модель игнорирует визуальный облик детали и генерирует «похожее по описанию», но не по внешнему виду.

**FLUX Inpainting** — облачная версия FLUX Fill с поддержкой маски. Для улучшения соответствия референсу в данной реализации применяется предварительная вставка изображения детали в центр маскированной области перед отправкой запроса. Это вынужденный приём, компенсирующий отсутствие нативной поддержки нескольких входных изображений.

**Мультиизображённое редактирование**

Ключевая проблема однообразного инпейнтинга — невозможность передать модели точный визуальный облик детали. Мультиизображённые модели решают эту задачу нативно: они принимают несколько изображений в одном запросе и на основе промпта самостоятельно определяют роль каждого.

**FLUX.2 Pro** (Black Forest Labs, ноябрь 2025) — модель следующего поколения с 32 млрд параметров. Принимает массив изображений произвольного размера в одном запросе. В данной работе используется как основная модель: маска передаётся первым изображением, референс детали — вторым, фото автомобиля — третьим, что позволяет модели самостоятельно интерпретировать роли входных данных на основе промпта. Обеспечивает наилучшее качество по соответствию референсу и фотореалистичности из всех исследованных моделей.

**GPT Image 1** (OpenAI) — закрытая проприетарная модель, недоступная для самостоятельного развёртывания. Поддерживает инпейнтинг через RGBA-маску, однако склонна перерисовывать изображение целиком, что снижает сохранность деталей вне области редактирования. Зависимость от коммерческого API-ключа OpenAI делает её неприемлемой для решений, требующих независимости от сторонних платформ.

**Img2img (без маски)**

**Flux 2 Klein** — быстрая модель img2img, принимает несколько входных изображений. Не поддерживает маску напрямую. Подходит для быстрого прототипирования результата без точной локализации.

**Flux Kontext** — редактирование на основе текстовой инструкции: изображение автомобиля и референс детали конкатенируются горизонтально в одно изображение, а инструкция в промпте указывает модели что и где изменить. Подход интересен простотой реализации, однако качество локализации уступает маскированному инпейнтингу.

## 1.5. Агентные системы на базе LLM

\ 

### 1.5.1. Мотивация агентного подхода

Пайплайн системы включает несколько разнородных шагов: интерпретацию запроса пользователя, семантический поиск по каталогу, сегментацию изображения и вызов модели инпейнтинга. Жёстко закодированная последовательность этих шагов плохо справляется с вариативностью входных данных: запрос «смени цвет дисков» требует иной логики сегментации, чем «поставь спойлер». Агентный подход позволяет делегировать принятие решений языковой модели: LLM самостоятельно определяет, какие инструменты вызвать и в каком порядке, основываясь на результатах предыдущих шагов.

### 1.5.2. Подходы к построению агентов

**Chain-of-Thought (CoT)** — модель рассуждает пошагово перед ответом, однако не взаимодействует с внешними системами. Применимо для задач, решаемых только на основе знаний модели, но не подходит для задач, требующих вызова API или обработки изображений.

**Plan-and-Execute** — агент сначала составляет полный план действий, затем выполняет его шаг за шагом. Недостаток: план фиксируется заранее и не корректируется при получении неожиданных результатов промежуточных шагов.

**Tool Calling** — модель вызывает инструменты напрямую без явного рассуждения. Подход быстрее, но менее прозрачен: сложно понять почему модель выбрала тот или иной инструмент.

**ReAct** (Reasoning + Acting, Yao et al., ICLR 2023) — модель чередует шаги рассуждения и действия: сначала формулирует мысль (*Thought*), затем вызывает инструмент (*Action*), получает результат (*Observation*) и на его основе формулирует следующую мысль. Цикл повторяется до финального ответа. Ключевое преимущество: агент динамически корректирует стратегию на основе промежуточных результатов.

| Подход | Внешние инструменты | Адаптация по ходу | Прозрачность |
|---|---|---|---|
| Chain-of-Thought | нет | нет | высокая |
| Plan-and-Execute | да | нет | средняя |
| Tool Calling | да | частично | низкая |
| ReAct | да | да | высокая |

### 1.5.3. Пример работы ReAct-агента

Для запроса пользователя «поставь карбоновый спойлер» агент выполняет следующий цикл:

*Thought:* Пользователь хочет установить карбоновый спойлер. Нужно сначала найти подходящую деталь в каталоге.

*Action:* `search_parts("карбоновый спойлер")`

*Observation:* `[{id: 42, name: "Спойлер карбоновый универсальный GT", image_url: "..."}]`

*Thought:* Деталь найдена. Теперь нужно выделить область на фотографии автомобиля, куда устанавливается спойлер.

*Action:* `segment_object("rear spoiler mount area")`

*Observation:* `{mask_url: "...", bbox: [120, 45, 380, 95]}`

*Thought:* Маска получена. Запускаю генерацию изображения с деталью и маской.

*Action:* `generate_image(part_id=42, mask_url="...")`

*Observation:* `{result_url: "...", status: "success"}`

*Final Answer:* Готово. Результат доступен по ссылке.

Такая трассировка полностью прозрачна: по логу агента можно точно понять, почему была выбрана та или иная деталь и какой регион изображения был изменён.

### 1.5.4. Сравнение фреймворков

**LlamaIndex** — специализируется на RAG и работе с документами. Подходит для систем вопрос-ответ над корпусом текстов, но не предназначен для оркестрации инструментов с побочными эффектами.

**AutoGen** (Microsoft) — ориентирован на мультиагентные системы, где несколько специализированных агентов взаимодействуют между собой. Избыточен для задач с линейным пайплайном.

**LangChain** — наиболее универсальный фреймворк с крупнейшим сообществом (80K+ звёзд на GitHub, 47 млн загрузок). Предоставляет декларативный API для описания инструментов и встроенную поддержку ReAct-агента через `create_react_agent`. Выбран в данной работе как стандарт индустрии для построения агентов с инструментами.

## 1.6. Семантический поиск и векторные базы данных

\ 

### 1.6.1. Принцип работы семантического поиска

Поиск по каталогу товаров на основе ключевых слов имеет фундаментальное ограничение: запрос «карбоновый спойлер GT» не найдёт позицию, названную «задний аэродинамический элемент из углеродного волокна», хотя семантически это одно и то же. Семантический поиск решает эту проблему через векторное представление текстов.

Модель-эмбеддер преобразует произвольный текст в числовой вектор фиксированной размерности (например, 384 числа), где близкие по смыслу тексты дают близкие векторы. Схожесть двух векторов измеряется через косинусное расстояние:

$$\text{sim}(A, B) = \frac{A \cdot B}{\|A\| \cdot \|B\|}$$

Значение 1,0 соответствует идентичным по смыслу текстам, 0,0 — не связанным. При поиске запрос пользователя преобразуется в вектор тем же эмбеддером, после чего база данных находит ближайшие по косинусному расстоянию векторы товаров из каталога. В данной работе используется порог схожести 0,4: результаты ниже этого значения считаются нерелевантными.

### 1.6.2. Модель эмбеддингов

**sentence-transformers/all-MiniLM-L6-v2** (Reimers & Gurevych, 2021) — компактная модель (22 млн параметров, 80 МБ) на базе дистиллированного MiniLM. Производит векторы размерностью 384. Обучена на 1 млрд пар предложений методом contrastive learning: пары семантически близких текстов притягиваются в пространстве эмбеддингов, несвязанные — отталкиваются. Несмотря на малый размер, занимает первые строчки в бенчмарках Massive Text Embedding Benchmark (MTEB) среди моделей своего класса. Поддерживает тексты на русском языке за счёт многоязычного предобучения бэкбона.

### 1.6.3. Сравнение векторных хранилищ

Для хранения эмбеддингов и выполнения векторного поиска рассматривались несколько решений.

**Pinecone** — полностью управляемый облачный сервис. Преимущество: не требует администрирования инфраструктуры. Недостаток: данные хранятся на сторонних серверах, что создаёт зависимость от вендора и потенциальные проблемы с конфиденциальностью.

**Weaviate** — открытая векторная база данных с собственным HTTP API и встроенной поддержкой нескольких эмбеддеров. Мощное решение для крупных продакшен-систем, однако требует отдельного развёртывания и операционных издержек.

**Qdrant** — открытая высокопроизводительная векторная база данных на Rust, ориентированная на скорость поиска при большом числе векторов. Как и Weaviate, требует отдельного сервиса.

**pgvector** — расширение для PostgreSQL, добавляющее тип данных `vector` и операторы косинусного, евклидова и inner product поиска. Поддерживает индексы HNSW и IVFFlat для ускорения поиска на больших объёмах. Ключевое преимущество для данного проекта: векторный поиск выполняется внутри той же базы данных, где хранятся остальные данные каталога, что исключает необходимость в дополнительном сервисе и упрощает транзакционную согласованность. Выбран в данной работе как оптимальное решение для встроенного семантического поиска без внешних зависимостей.

| Решение | Тип | Инфраструктура | Транзакции с SQL | Подходит для |
|---|---|---|---|---|
| Pinecone | облачный SaaS | не требуется | нет | быстрый старт |
| Weaviate | open-source | отдельный сервис | нет | крупные системы |
| Qdrant | open-source | отдельный сервис | нет | высокая нагрузка |
| pgvector | расширение PostgreSQL | в основной БД | да | единая БД |
