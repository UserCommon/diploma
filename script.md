→ Слайд 2 (Проблема дистанционной торговли)

Объём e-commerce в России в прошлом году превысил 11 триллионов рублей — рост 41% за год. Это огромный рынок. Но у него есть структурная проблема: покупатель принимает решение только по фотографии — он не может ни потрогать товар, ни примерить его. Для обычной одежды это терпимо. Но для автотюнинга или интерьера — физическая примерка невозможна в принципе.

Этот год сделал проблему массовой: Wildberries и Ozon ввели платные возвраты. Люди заказывают — не то, что ожидали — возвращают. И платят.

→ Слайд 3 (Возвраты — макроэкономическая проблема)

Это не только российская история. В США в 2024 году объём товарных возвратов составил 890 миллиардов долларов. Обработка одного возврата обходится продавцу в 20–66% от стоимости товара — это логистика, переупаковка, потери.

Исследования показывают: AI-визуализация снижает возвраты на 30–40%. И рынок это чувствует — сегмент виртуальной примерки вырастет с 11 до 46 миллиардов долларов к 2030 году.

Казалось бы — решение очевидно. Но почему его до сих пор нет?

→ Слайд 4 (Почему существующие решения не подходят)

Потому что все существующие решения заточены под одну категорию. Zalando, Amazon, Google — только одежда. IKEA Place — только мебель, и только если у производителя есть 3D-модель каждого товара.

Главное ограничение: никто не умеет работать с произвольным текстовым запросом. Ты не можешь написать «поставь карбоновый спойлер» и получить результат. Нужна ручная разметка, нужна 3D-модель, нужен конкретный пайплайн под конкретную категорию.

Мы сделали иначе.

→ Слайд 5 (Наше решение)

TuneAI — система, которая принимает фото и текст и возвращает фотореалистичный результат. Без разметки. Без выбора параметров. Без категорийных ограничений.

Пользователь загружает фото автомобиля, пишет — «поставь карбоновый спойлер» — и система сама находит деталь в каталоге, выделяет нужную область на машине и генерирует результат. Давайте посмотрим, как это выглядит.

→ Слайд 10 (Архитектура системы)

Архитектура — микросервисная. Фронтенд на SvelteKit общается с core_service на FastAPI: HTTP REST для команд и SSE-стриминг для живых обновлений в интерфейсе — пользователь видит прогресс в реальном времени.

core_service работает с PostgreSQL и ставит задачи в Redis через очередь SAQ. Дальше задачи разбирают два воркера параллельно: core_worker — это ReAct-агент, он занимается сегментацией и генерацией, accessories_worker — поиск по эмбеддингам. Такая архитектура позволяет масштабировать каждый компонент независимо.

→ Слайд 11 (Пайплайн)

Внутри агента — шесть шагов: запрос → LLM-агент → поиск детали через pgvector → сегментация через GroundingDINO и SAM 2 → генерация через FLUX.2 Pro → результат.

Ключевой момент: это не жёсткий скрипт. Агент сам решает порядок действий и обрабатывает ошибки — это ReAct-архитектура, «рассуждение плюс действие» в цикле.

→ Слайд 12 (Технологический стек)

Технологический стек: LangChain ReAct для агента, GroundingDINO и SAM 2 для сегментации, FLUX.2 Pro — модель на 32 миллиарда параметров для генерации, sentence-transformers и pgvector для поиска, FastAPI с SAQ на бэкенде, SvelteKit на фронте.

→ Слайд 13 (Результаты тестирования)

Тестирование: 73 сессии, 94,5% завершились успешно. CLIP Score — 0,195, это норма для задач локального редактирования изображений. Поиск — Precision@1 = 0,70, латентность 25 миллисекунд.

Выявлена одна точка роста: русскоязычные запросы работают чуть хуже — каталог на английском, и при переводе теряется точность. Это направление следующей итерации.

Возможные вопросы комиссии — и как отвечать

«Почему FLUX, а не Stable Diffusion?» FLUX.2 Pro — актуальное поколение, 32 млрд параметров против ~1 млрд у SD. Качество инпейнтинга на реальных фото значительно выше, особенно при сохранении фона.

«CLIP Score 0,195 — это хорошо или плохо?» Для задач глобальной генерации норма — 0,25–0,35. Но мы решаем задачу локального редактирования: меняется небольшая область, фон остаётся. Метрика считается по всему изображению — поэтому 0,195 адекватен для данной задачи.

«Как масштабируется система?» Воркеры независимы и запускаются в Docker. Можно горизонтально масштабировать accessories_worker под нагрузку поиска и core_worker под нагрузку генерации — они не связаны.

«Почему 5,5% сессий упало?» Тайм-ауты при обращении к внешнему API FLUX в периоды высокой нагрузки. Решается retry-логикой и fallback на локальную модель.
